# advanced-QODE

**advanced-QODE** (Quality & Optimization of DevSecOps Engineering) is a toolset for performing next-level DevSecOps assessments based on the **9 core pillars of the Software Development Life Cycle (SDLC)**. It ingests a structured questionnaire (Excel workbook), analyses the answered user stories, and produces three Graphviz-based visualisation diagrams together with an automated Word report — giving teams a clear, data-driven picture of their current DevSecOps maturity.

## Project Overview

DevSecOps assessments traditionally require hours of manual effort to translate questionnaire responses into coherent process maps, stakeholder diagrams, and tool-integration charts. **advanced-QODE** automates this translation:

1. A consultant fills in the `QODE-Questionnaire.xlsm` workbook, selecting which SDLC activities apply ("Yes") and describing their timing, ownership, predecessors, and tooling.
2. Three Python scripts read the workbook and produce **Graphviz DOT files** that visualise:
   - The **end-to-end process flow** (with lead-time and critical-path calculations).
   - The **people / team-role collaboration network**.
   - The **technology / automation-tool integration map**.
3. A Google Colab notebook reads a separate source-data spreadsheet, substitutes variables into a Word report template, and saves a completed assessment report.

The resulting artefacts accelerate executive reporting, gap analysis, and continuous-improvement planning across all nine SDLC pillars.

## Core Concepts

| Term | Meaning |
|------|---------|
| **QODE** | Quality & Optimization of DevSecOps Engineering — the assessment framework. |
| **DQODE** | The diagnostic/report variant of QODE; the Word report generated by the Colab script. |
| **Q_Stories** | The Excel sheet (inside `QODE-Questionnaire.xlsm`) that lists every SDLC activity as a "story". |
| **User Story (S#)** | A numbered row in Q_Stories representing a discrete SDLC activity. |
| **Node / Event (E#)** | Each accepted user story becomes a node in the process network diagram. `E0` is the fixed starting node (Requirement / Jira). |
| **Activity (A#)** | The directed edge connecting two nodes; labelled with timing and team information. |
| **Critical Path** | The longest-duration path through the network that ends at a *Material* output node — this is the bottleneck of the SDLC process. |
| **Criticality** | A per-activity priority score: `Hi` = 3, `Med` = 2, `Lo` = 1. Used to break ties between paths of equal duration. |

## Input Data Model

The primary input is `QODE-Questionnaire.xlsm`, sheet **Q_Stories** (data starts at row 4, with an additional two-row offset applied at read time).

### Required columns

| Column | Description |
|--------|-------------|
| `S#` | Unique identifier for the user story / activity. |
| `Yes / No` | Only rows with value `Yes` are included in diagrams. |
| `Total time taken` | Total elapsed time (in consistent units, e.g. hours or days) for the activity. |
| `Manual time spent` | Portion of total time that is manual (non-automated). When `Total – Manual ≠ 0`, the edge is drawn in black; otherwise orange, indicating a fully manual step. |
| `Predecessor 1 (incl. INIT)` | The `S#` of the directly preceding activity, or `INIT` for the first activity in a parallel stream. |
| `Predecessor 2–5 (optional)` | Up to four additional predecessors, enabling parallel / merge patterns. |
| `Criticality` | Priority level: `Hi`, `Med`, or `Lo`. |
| `Team / owner role` | The team or role responsible for this activity (used in the People diagram). |
| `Input` | Description of inputs consumed by the activity. |
| `Output` | Description of outputs produced by the activity. |
| `Output type` | `Material` (a tangible deliverable) or other. Only `Material` leaf nodes are considered as valid end-points for critical-path analysis. |
| `Automation tool` | The tool that automates (fully or partially) this activity (used in the Technology diagram). |

### Report source data (`DQODE_Report_Source_Data_Excel.xlsx`)

Used exclusively by the Colab report generator. Key cells in the active sheet:

| Cell | Variable |
|------|----------|
| B2 | Application name |
| B3 | Consultant name |
| B4 | Client name |
| B5 | About the customer |
| B6 | Problem statement |
| B7 | Month of assessment |
| B8 | As-is roles |
| B9–B10 | Process variables 1–2 |
| B11–B16 | Architecture variables 1–6 |
| B17–B25 | Key-component variables 1–9 |
| B26 | Improvement variable 1 |

## Components

### Generate_Process_Network_Diagram.py

**Purpose:** Produces a directed process-network (flow) diagram that shows every active SDLC activity as a node, the dependencies between activities as edges, and highlights the **critical path** — the longest, highest-criticality route from requirement intake to final material output.

**Algorithm overview:**

1. **Data ingestion** — reads the `Q_Stories` sheet and filters to rows where `Yes / No == 'Yes'`.
2. **Node creation** — builds a `pydot` (Graphviz) node per activity, plus a root node `E0` representing the Requirement (Jira) entry point.
3. **Lead-time calculation** — performs two forward-pass sweeps over the predecessor relationships to compute the earliest-completion time of each node. This is an approximation of the classic PERT/CPM forward pass.
4. **Edge creation** — connects nodes with labelled edges showing activity ID, timing, predecessor completion time, and team/owner role.
5. **NetworkX graph** — a parallel `networkx.DiGraph` is built to enable algorithmic path analysis.
6. **Critical-path analysis:**
   - Identifies leaf nodes (no successors).
   - Filters to leaf nodes with `Output type == 'Material'`.
   - Finds the node(s) with the maximum lead time (i.e., the longest path).
   - Among equal-duration paths, selects those with the highest average criticality.
   - Among remaining ties, selects the path(s) with the most nodes (greatest granularity).
7. **Output** — writes a Graphviz DOT file named `Diagram_Network`.

**Key class:** `Process_Diagram`

| Method | Responsibility |
|--------|---------------|
| `node_creation` | Creates a `pydot.Node` with colour and shape. |
| `edge_creation` | Creates a labelled `pydot.Edge`. |
| `calculate_lead_time` | Computes cumulative lead time for each node via predecessor traversal. |
| `pydot_node_creation` | Builds all Graphviz nodes from the filtered DataFrame. |
| `pydot_edge_creation` | Builds all Graphviz edges with timing labels. |
| `networkX_node_creation` | Mirrors node creation in `networkx`. |
| `networkX_edge_creation` | Mirrors edge creation in `networkx`. |
| `find_leafnodes` | Returns nodes with no successors that also have a unique root ancestor. |
| `find_critical_paths` | Orchestrates the full critical-path selection logic. |
| `new_avg_criticality` | Computes the average criticality score of a given path. |
| `node_to_edge` | Converts a node path to the list of edge labels along that path. |
| `output` | Writes the final DOT file. |
| `create_network_diagram` | Top-level method — orchestrates the entire pipeline. |

---

### Generate_People_Diagram.py

**Purpose:** Produces a directed **team-role collaboration diagram** that shows which roles hand work off to which other roles, and whether those hand-offs are automated (black edge) or fully manual (orange edge).

**Algorithm overview:**

1. **Data ingestion** — same filtered DataFrame as the Process diagram.
2. **Node creation** — one node per distinct value in `Team / owner role`.
3. **Edge creation** — for each activity, an edge is drawn from each predecessor's owning role to the current activity's owning role. Edge colour encodes automation level:
   - **Black** — at least some automation exists (`Total time – Manual time ≠ 0`).
   - **Orange** — fully manual step.
4. **Output** — writes `Diagram_People`.

**Key class:** `People_Diagram`

| Method | Responsibility |
|--------|---------------|
| `node_creation` | Creates one Graphviz node per unique role. |
| `edge_creation` | Creates a thin, decorated `pydot.Edge` between roles. |
| `create_edge` | Iterates all activities and adds inter-role edges with appropriate colour. |
| `output` | Writes the final DOT file. |
| `create_people_diagram` | Top-level orchestration method. |

---

### Generate_Technology_Diagram.py

**Purpose:** Produces a directed **technology/toolchain integration diagram** showing which automation tools feed into each other across the SDLC pipeline, and which activities (A#) drive each tool-to-tool handover.

**Algorithm overview:**

1. **Data ingestion** — same filtered DataFrame.
2. **Node creation** — one node per distinct value in `Automation tool`.
3. **Edge deduplication** — the `check_edge_present` method accumulates activity labels on an existing edge rather than creating duplicate edges between the same tool pair.
4. **Edge creation** — after deduplication, all aggregated edges are added to the Graphviz graph.
5. **Output** — writes `Diagram_Technology`.

**Key class:** `Technology_Diagram`

| Method | Responsibility |
|--------|---------------|
| `node_creation` | Creates one Graphviz node per unique automation tool. |
| `check_edge_present` | Deduplicates edges; appends activity label to an existing edge when the same tool pair is encountered again. |
| `edge_creation` | Creates a small-font, black `pydot.Edge` with an aggregated label. |
| `create_edge` | Iterates activities and builds the deduplication list. |
| `output` | Writes the final DOT file. |
| `create_technology_diagram` | Top-level orchestration method. |

### Auto DQODE Report Generation

**File:** `Auto_DQODE_Report_ Generation.txt`

**Purpose:** A **Google Colab** Python script that automates the population of a Word (.docx) assessment report from a structured Excel data file.

**Workflow:**

1. Upload `DQODE_Report_Source_Data_Excel.xlsx` via the Colab file picker.
2. Upload `TCS_TestReport_Template_with_Variable.docx` (a Word template containing `$variable_name$` placeholders).
3. The script reads metadata, process variables, architecture variables, key-component variables, and improvement items from the Excel file.
4. It constructs a `replacement` dictionary mapping each `$placeholder$` to its Excel-sourced value.
5. It iterates over every paragraph in the Word document and performs string substitution.
6. The completed document is saved as `test_doc_updated.docx`.

**Template variable reference:**

| Placeholder | Source |
|-------------|--------|
| `$application_name$` | Excel B2 |
| `$consultant_name$` | Excel B3 |
| `$client_name$` | Excel B4 |
| `$bank_name$` | Hard-coded as `BANK-OF-TCS` |
| `$about_customer$` | Excel B5 |
| `$problem_statement$` | Excel B6 |
| `$months$` | Excel B7 |
| `$process_variable1/2$` | Excel B9–B10 |
| `$arch_variable1–6$` | Excel B11–B16 |
| `$keycomp_variable1–9$` | Excel B17–B25 |
| `$improvement_variable1$` | Excel B26 |
| `$role_array$` | Excel B8 (as-is roles) |
| `$role_utilization_table$` | Hard-coded role utilisation descriptions |
| `$date$` | Today's date (auto-generated) |

## Setup & Installation

### Prerequisites

- Python 3.8 or higher
- [Graphviz](https://graphviz.org/download/) installed on the system PATH (required by `pydot` to render DOT files)

### First-time setup

```bash
# 1. Create and activate a virtual environment
python -m venv venv

# Windows
.\venv\Scripts\activate.bat

# macOS / Linux
source venv/bin/activate

# 2. Install Python dependencies
pip install -r requirement.txt
```

> **Note:** If a `requirement.txt` is not present, install the packages listed in [Dependencies](#dependencies) manually.

### Prepare the questionnaire

Place your completed `QODE-Questionnaire.xlsm` workbook in the same directory as the Python scripts. A `sample_questions.xlsm` file is provided as a reference template.

## Usage

Run each diagram generator independently from the project root:

```bash
# Process network diagram (critical-path analysis)
python Generate_Process_Network_Diagram.py

# People / team-role collaboration diagram
python Generate_People_Diagram.py

# Technology / toolchain integration diagram
python Generate_Technology_Diagram.py
```

Each script reads `QODE-Questionnaire.xlsm` from the current directory and writes a Graphviz DOT file.

For the **automated Word report**, paste the contents of `Auto_DQODE_Report_ Generation.txt` into a Google Colab notebook and follow the upload prompts.

## Visualising the Diagrams

The `.dot` output files can be rendered in several ways:

1. **Online (recommended for quick review):**
   Copy the contents of a `Diagram_*` file and paste into the [Graphviz Online Visualiser](https://dreampuf.github.io/GraphvizOnline/).

2. **Command-line (requires local Graphviz):**
   ```bash
   dot -Tpng Diagram_Network -o Network_Diagram.png
   dot -Tsvg Diagram_People  -o People_Diagram.svg
   dot -Tpng Diagram_Technology -o Technology_Diagram.png
   ```

3. **VS Code:** Install the *Graphviz (dot) language support* extension to preview DOT files directly in the editor.
